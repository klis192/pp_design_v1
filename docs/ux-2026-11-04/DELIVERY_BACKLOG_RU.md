# Поставка всего ТЗ: сценарии, исполнители и приёмка

Этот backlog назначает **все 155 исходных формулировок** одному основному пакету работ. Повторяющиеся требования сохранены отдельно; составные строки требуют также перечисленные дополнительные пакеты. Так нельзя закрыть одну часть строки и потерять другую. Это план работ и доказательств, а не сообщение о завершённой разработке.

Базовая матрица: [requirements-matrix.json](requirements-matrix.json), исходный код `85f8e146869ae71f129d67b5dbf31a7eb512f9ef`; исходная DOCX SHA256 `efbb3352de407c93668f242d4716b29ac9ae9eea39a1618fad36196bceeb4a01`. Этапы соответствуют [DELIVERY_PLAN_RU.md](DELIVERY_PLAN_RU.md). Машиночитаемый реестр: [delivery-backlog.json](delivery-backlog.json).

Матрица зафиксирована статическим чтением. В этом документном проходе не запускались продуктовые тесты, устройства, 1С, обмен или production. Новые локальные исправления UI foundation не повышают исходный статус до полной приёмки. Колонка «Статус среза» сохраняет исходную оценку, это не переоценка текущего кода. Число строк не является процентом готовности.

Правило пользователя: у каждой роли свои приоритеты. Бизнес-персоны ниже — не новые технические enum-роли и не основание расширять права. Собственник не получает финансовые ЛС арендатора автоматически.

## Как исполнять

- У каждого ID ровно один `primaryWorkPackageId`. Дополнительные пакеты и их критерии обязательны для составного текста. Они связывают результаты, но не добавляют второе основное назначение или циклические зависимости разработки.
- Владелец пакета координирует, исполнители меняют свой слой, review проверяет независимо. Это профили специалистов, не утверждение о назначении конкретного человека. Бизнес-правила утверждают указанные бизнес-владельцы.
- Каждый пакет имеет три конкретных критерия: обычный сценарий, исключение/повтор/конфликт и права либо независимую сверку. Доказательство содержит версию, среду, данные/роли, шаги, expected/actual, а для runtime — журналы/скриншоты/ID без секретов.
- Внешняя зависимость не останавливает независимый код, но блокирует настоящую приёмку. OTP, полномочия, подпись, push и бухгалтерское проведение нельзя подменять имитацией.
- Номер этапа — место в плане. Контракты 1С/доступа/уведомлений согласуются параллельно; финальная приёмка учитывает зависимости. WP-01 начинается на этапе1, общие поверхности завершаются на этапе3.
- BP-01…12 соответствуют [каталогу процессов](FUNCTIONS_AND_WORKFLOWS_RU.md). EXT-01…07 и OPS-01 — ниже определённые планируемые процессы следующего этапа/эксплуатации, а не обнаруженные готовые модули.
